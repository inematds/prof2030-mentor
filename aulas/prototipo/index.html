Aula 3 · 20 min

Protótipo em um dia

Com a spec aprovada, o gestor monta o primeiro protótipo numa sessão de trabalho com você. Ele dirige o teclado; você segura o escopo, os dados fictícios e a conferência. No fim do dia há uma ferramenta rodando no computador dele e uma lista honesta do que falta.

Começar a aula

Nesta aula você vai

  1. 1Preparar a pasta com regras e dados fictícios
  2. 2Pedir só o que está na spec
  3. 3Conferir com três casos
  4. 4Salvar, desfazer e anotar lacunas

Objetivo: conduzir a sessão em que o gestor monta o protótipo com um agente, com dados fictícios, Git e lista de lacunas.

01 · O ciclo da sessão de protótipo

Cinco etapas, repetidas até o fim do dia. Clique em cada bloco.

Preparar

Role a página: cada etapa abaixo acende a sua parte do diagrama.

  1. 1/6

    Preparar

    Uma pasta só para o protótipo, com o AGENTS.md (o manual que o agente lê antes de trabalhar), a spec e uma planilha de dados inventados. Nenhum dado real de cliente entra hoje.

  2. 2/6

    Pedir

    O gestor pede ao agente uma coisa só, com o resultado esperado. Pedido grande demais gera mudança que ninguém consegue conferir.

  3. 3/6

    Agente constrói

    Um agente de código no terminal ou o agente de trabalho do app de chat. Qual usar depende do que a empresa já tem; a lista do mês está na aula 8. O método é o mesmo.

  4. 4/6

    Conferir

    Abrir e testar com um caso comum, uma exceção e um dado faltando. "Abriu e ficou bonito" não é conferir.

  5. 5/6

    Salvar ou desfazer

    Gostou: commit. Não gostou: git restore. Tudo o que o agente fez sem a spec mandar vira linha no lacunas.md, que alimenta a constituição (aula 4) e os testes (aula 5).

  6. 6/6

    Um dia, várias voltas

    Preparar uma vez; depois pedir, construir, conferir e salvar quantas vezes for preciso. O que sobra no fim é um protótipo que roda e uma lista de lacunas.

Quem digita é o gestor. O mentor pergunta, aponta e confere.

02 · A sessão em quatro blocos

Um dia de trabalho, ou duas meias manhãs.

1. Antes da sessão

Combine o equipamento: notebook do gestor, conta da empresa no agente escolhido, Git instalado. Gere com ele uma planilha de 20 clientes inventados, com nomes e valores fictícios.

Antes de construir, vale um ensaio: colar a spec num chat e pedir que ele faça o papel da ferramenta num caso. As perguntas que ele fizer mostram lacunas da spec.

Regra do diaNenhum dado real de cliente. Nenhuma chave de API no navegador.

2. Manhã

O gestor cria a pasta, o AGENTS.md e faz o primeiro commit. Primeiro pedido: só leitura ("leia o AGENTS.md e a spec e diga o que entendeu").

Segundo pedido: a lista de orçamentos abertos com a regra da spec. Abrir, conferir, salvar.

Sinal de que está indo bemNa hora do almoço o gestor já pede sozinho e sabe voltar uma versão com git restore.

3. Tarde

Terceiro pedido: o rascunho de mensagem para cada orçamento, citando só produtos do catálogo. Quarto: o botão de aprovar e a exportação do que foi aprovado.

Envio automático, WhatsApp oficial e desconto ficam fora: não estão na spec v0.1.

Na HorizonteA Patrícia aprovou 12 rascunhos fictícios em 10 minutos e editou 3. Isso já é um número para a aula 7.

4. Fechamento

Rodem os três casos de conferência. Tudo o que surpreendeu vai para o lacunas.md com data, o que aconteceu e o que deveria ter acontecido.

Combine a próxima sessão: escrever a constituição com base nas lacunas.

Entrega do diaProtótipo rodando + histórico no Git + lacunas.md com pelo menos três linhas.

AGENTS.md do protótipo
# Projeto: follow-up de orçamentos (protótipo v0.1)
Dona: Patrícia Lima, gerente comercial · Mentor: <nome> · TI: Rafael

## Regras
- Siga a spec.md. Se algo não estiver nela, PERGUNTE antes de fazer.
- Use só os dados da pasta dados-ficticios/. Nunca peça nem use dado real.
- Não coloque chave de API, senha ou token em nenhum arquivo.
- Não crie envio automático de mensagem, desconto ou alteração de preço.
- Página simples em HTML que abre no navegador, sem servidor.
- Ao terminar cada tarefa: diga o que mudou e como eu confiro.

## O que tem aqui
- spec.md: a spec de uma página
- dados-ficticios/orcamentos.csv: 20 orçamentos inventados
- lacunas.md: o que o protótipo ainda não resolve
Prompt de protótipo (primeiro pedido de construção)
Leia o AGENTS.md e a spec.md antes de começar.

Tarefa: crie index.html, uma página que abre no navegador e:
1. carrega dados-ficticios/orcamentos.csv;
2. mostra só os orçamentos abertos há 2 dias úteis ou mais, de clientes ativos;
3. para cada um, mostra um rascunho de mensagem curta (até 5 linhas) que cita o último
   produto comprado e termina com uma pergunta;
4. tem um botão "Aprovar" por linha e um botão "Exportar aprovados" que baixa um CSV.

Não faça: envio de mensagem, desconto, mudança de preço, chave de API.
Se faltar alguma regra para decidir, pare e me pergunte citando a seção da spec.
No fim, diga o que criou e como eu confiro em 3 casos.
Simulação: exemplo ilustrativo
  1. A página abre no navegador do gestor sem servidor e sem chave.
  2. Só aparecem orçamentos que a regra da spec manda mostrar.
  3. Nenhum rascunho cita produto fora do catálogo ou desconto.
  4. git log mostra um commit por pedido.
  • Dado real "só para ver": uma vez dentro do chat, já saiu da empresa.
  • Mentor no teclado: o protótipo fica sem dono.
  • Pedido de tudo de uma vez: mudança que ninguém confere e escopo que estoura.
  • Chave de API no HTML: é a falha F1 do laboratório.
