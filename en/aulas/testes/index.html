Lesson 5 · 20 min

Test before you turn it on

"It worked" doesn't tell you in how many cases, or which error slipped through. Before any real use, the mentor and the manager build a test suite with the right answer written down before running, score it with criteria you can count, and only then call the user in to run acceptance testing.

Start the lesson

In this lesson you will

  1. 1Build 15 cases with the answer written first
  2. 2Score on four criteria
  3. 3Adjust one thing per round
  4. 4Run acceptance testing with the user

Goal: build a test suite of 15 cases with expected answers, run it with objective scoring, and run acceptance testing with the user at a clear gate.

  1. 1/7

    Cases

    About 60% common, 30% exceptions, and 10% hard. Include cases where the right move is to call a person, a forbidden request, and an order hidden in the customer's text.

  2. 2/7

    Expected first

    The right answer and the decision (proceed, ask, or escalate) are written before running, by the manager. Without that, a score is just an impression.

  3. 3/7

    Run

    Run the whole suite and keep the output of each case. Every new version runs the same 15.

  4. 4/7

    Score

    A case only passes if it gets all four criteria right. One violated limit fails the entire run, even with many correct answers.

  5. 5/7

    Adjust

    Change one thing (one line of the constitution, one example), version it with the reason, and run everything again. Make two changes together and nobody knows which one worked.

  6. 6/7

    Run acceptance testing

    Meeting with the manager: live demo, the test suite report, signed permissions, and a plan for switching it off. If she hesitates, it's not ready yet.

  7. 7/7

    The whole cycle

    Cases with the right answer written beforehand, a full round, a score on four criteria, one change at a time, and user acceptance testing.

15 cases are enough for the prototype. Before production, IT and the manager expand it to 30 to 50 real, anonymized cases.

02 · How to run the tests

Click each step.

1. Build the cases

The best cases come from the real history, with names and phone numbers swapped for fictitious ones. Add the prototype's gaps and the hard cases from the constitution.

Don't use as tests the examples you gave the agent to learn from: the test and the example must be different.

MinimumAt least 2 cases where the right move is to escalate, 1 forbidden request, and 1 order hidden in the customer's text.

2. Score in a way you can count

Decision: did it proceed, ask, or escalate as it should? Rule: did it respect the constitution? Data: did it use only what it could, without making things up? Tone: short, polite, with one question?

No 1-to-10 scores. Yes or no, per criterion, per case.

Scorecard for one roundCorrect 13 of 15 · escalated when it should have 2 of 2 · limit violated: no · decision: approve for acceptance testing.

3. Gate for acceptance testing

A floor used in the deployment method this lesson builds on: 85% or more correct and no limit violated. Between 70% and 85%, adjust and run again. Below 70%, the problem is in the design: go back to the spec.

Don't chase 100%. If three or four rounds don't converge, the problem isn't the wording.

In 15 cases85% = 13 correct. With 12, it doesn't pass acceptance testing yet.

4. Run acceptance testing with the user

Live demo of 5 to 8 cases, including one where the tool escalates. Test suite report. The manager signs the permissions. Quick training on how to pause it.

Final question, asked separately: "Do you feel comfortable using it?" If the answer isn't yes, run one more simulation session first.

At HorizontePatrícia asked for one more case: a customer who replies with just "?". It went into the test suite as case 16.

Acceptance testing script with the user (75 min)
ACCEPTANCE TESTING · tool: <name> · user/owner: <name> · date: <dd/mm>

0–5    Agree: today we decide whether it goes to the handoff to IT
5–30   Live demo of 5 to 8 cases (includes 1 that escalates)
30–45  Test suite report: correct answers, top 3 errors, adjustments made
45–55  Owner signs the permissions matrix and the constitution
55–65  Training: how to pause it, where to see the log, who to call
65–75  Exit gate

GATE (all yes)
[ ] >= 85% on the test suite and no limit violated
[ ] permissions and constitution signed by the owner
[ ] owner states she feels comfortable (separate question)
[ ] there is a documented way to switch it off in minutes
[ ] list of what is still missing for production (goes to IT)

If it did not pass: record the reason and set a new date in 7 to 14 days.
Simulation: illustrative example
  1. v1.0: 12 of 15. Failed case 11 (promised "delivery tomorrow") and case 14 (approved). Failed: limit violated.
  2. Single change: hard case "order inside the text" added to the constitution.
  3. v1.1: 13 of 15, no critical case failed. Goes to acceptance testing.
  • Expected answer written afterward: it becomes a justification of what came out.
  • Two changes in the same round: nobody knows which one fixed it.
  • High average hiding a critical failure: 14 of 15 with a discount granted is a fail.

04 · Practice: test suite and acceptance testing

With the manager and the prototype from lesson 3.

E1 · 15 cases

60 min

Build the test suite with the manager from the history (swapped data), the gaps, and the hard cases.

Done when: 15 rows with expected answer and decision, at least 2 escalations, 1 forbidden request, and 1 hidden instruction.

E2 · Rounds

90 min

Run the test suite, score the 4 criteria, make one change per round.

Done when: there is a round with 13 of 15 or more and no critical case failed, with the annotated version.

E3 · User acceptance testing

75 min

Lead the meeting with the user using the script.

Done when: the 5 gate items are checked, or there is a new date with the reason recorded.
